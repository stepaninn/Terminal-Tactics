# Тестирование и качество кода

Основная логика проекта покрыта unit-тестами на Catch2. Тесты лежат в `tests` и разделены по тем же зонам ответственности, что и основной код

## Unit-тесты

- `test_matrix.cpp` - собственный контейнер `Matrix`, итераторы, доступ по индексам, resize, copy/move семантика
- `test_cells.cpp` - клетки уровня, контейнеры предметов, разрушаемые клетки, тайники и стекло
- `test_components.cpp` - компоненты здоровья, очков времени, движения, обзора, боя, ИИ, инвентаря и оружия
- `test_items.cpp` - предметы, оружие, аптечки и подсумки с патронами
- `test_entities.cpp` - добавление, получение, замена и удаление компонентов у сущностей
- `test_factory.cpp` - корректная сборка оперативников и разных типов врагов через `EntityFactory`
- `test_level.cpp` - хранение сущностей, позиций, клеток и предметов на уровне
- `test_service.cpp` - основные игровые правила: ходы, движение, бой, инвентарь, использование предметов, видимость, ИИ, события и сохранение/загрузка
- `test_mt.cpp` - конкурентный доступ к уровню и компонентам, порядок парных блокировок и параллельное обновление команды; собирается при `TERMINAL_TACTICS_BUILD_MT=ON`

Покрытие ядра проекта и сервисов составляет около 90%. Основной акцент в тестах сделан на модель и сервисы, потому что именно там находится игровая логика. Терминальный UI на ncurses проверялся вручную: он тонкий слой над контроллером и в основном отвечает за отображение и преобразование клавиш в `InputAction`

## Анализаторы

При разработке дополнительно использовались статические и динамические анализаторы:

- `clang-tidy` - поиск проблем в C++-коде, подозрительных конструкций и нарушений современных практик
- `cppcheck` - дополнительная независимая статическая проверка
- `valgrind` - проверка ошибок работы с памятью в однопоточной версии
- `ThreadSanitizer` - проверка многопоточной версии на data race

Для многопоточной версии отдельно проверялись сценарии параллельной обработки ходов ИИ, взаимодействия сущностей, инвентаря и боя. В `_mt`-версии изменяемые компоненты защищены с помощью mutex, общие структуры частично перенесены на TBB-контейнеры, а операции над одной или двумя сущностями синхронизируются через `EntityLockPool`. Текущий регрессионный набор также проверяет отсутствие повторного захвата блокировки при поиске сущности и разрушении клетки

## Запуск тестов

Самый короткий воспроизводимый запуск не требует локального C++ toolchain:

```bash
make docker-test
```

Цель `docker-test` вызывает Docker Compose. Контейнер собирает однопоточную и многопоточную библиотеки и запускает все зарегистрированные CTest-цели. Тот же сценарий выполняется отдельной job в GitHub Actions

После локальной сборки тесты можно запустить через CTest:

```bash
make test
```

Также собирается общий исполняемый файл со всеми тестами:

```bash
./build/tests/test_all
```

`test_all` относится к однопоточной версии. Для запуска в том числе конкурентных тестов нужно включить `TERMINAL_TACTICS_BUILD_MT=ON` и использовать CTest либо запустить `./build-mt/tests/test_mt`

Для воспроизводимых конфигураций добавлены CMake presets:

```bash
cmake --preset docker-tests
cmake --build --preset docker-tests
ctest --preset docker-tests
```

Основные команды собраны в `Makefile`:

- `make build` и `make test` - обычная версия
- `make mt-build` и `make mt-test` - сборка и тестирование обеих версий
- `make docker-test` - полный тестовый прогон без локального toolchain
- `make tsan-test` - MT-сборка и тесты с ThreadSanitizer
